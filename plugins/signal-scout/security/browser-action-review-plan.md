Updated: 2026-09-16. Status: interview/design, not a confirmed coding brief.

This document consolidates the browser-action and security discussion, with
project context and links to earlier plans. It distinguishes decisions from
proposals and implemented protections. It is not a claim that reviewed browsing

Implementation note, 2026-10-09: standalone safety-reviewer client now lives in

## 1. Project direction and scope

- Signal Scout researches competitors and demand signals for `freepik_clone`:
  useful features, tutorials, ads, short-form content, and longer AI-generated
  media. Desired output: evidence-backed product opportunities, not just links.
- Discovery is not intended to be an unbiased sample of media prevalence.
  User welcomes Scout-specific personalization that exposes more AI-media products
  and use cases. This does not authorize importing personal browser profiles.
- Build on the Hermes fork and reuse native browser/plugin/model infrastructure.
  Do not build another browser automation engine or rewrite Hermes unnecessarily.
- Code owns enforceable boundaries, persistence, usage accounting, and tests.
  LLM instructions own research strategy, interpretation, and synthesis.
- Development stays local; selected eventual deployment is an OVHcloud VPS-2.
  Cloud hardware ownership does not remove responsibility for guest security,
  credentials, software updates, or activity generated by Scout.
- Existing model access uses the user's OpenAI subscription through Hermes.
  A separate reviewer does not imply a separately purchased subscription, but
  its model calls still consume usage. Initial reviewer: `gpt-5.6-luna`, medium
  reasoning, configurable separately from the research model; no model fallback.
- Long-term target: roughly 50% of daily Codex allowance, intermittent findings,
  and a final surfing summary. Authoritative allowance measurement is unresolved;
  raw token estimates are not a substitute for that percentage.
- Future messaging through Discord, WhatsApp, or another service must remain
  possible. Platform choice and implementation are not part of this slice.
- Media preprocessing remains future work: sampled frames/scene changes,
  timestamped transcription, and synchronized evidence instead of every frame.
  No CRV or other analyzer integration is approved by this browser discussion.
- Source accounts must be Scout-specific, not personal browser profiles/cookies.
  Current work concerns anonymous browsing, not social-account provisioning.

## 2. Existing implementation versus planned work

Implemented protection-only baseline, documented in [security README](README.md)
and [Docker README](../../../docker/signal-scout/README.md):

- Native status-only Scout plugin and bounded subscription-backed status chat.
  The model does not yet receive Scout browser tools.
- Trusted deterministic browser harness using pinned `agent-browser 0.26.0` and
  local Chromium. Fresh anonymous profile; actual sandbox attestation required.
- Non-root Scout container, read-only root filesystem, dropped capabilities,
  restricted seccomp, resource limits, and temporary `/tmp` storage.
- Raw URL syntax/scheme/credential checks in Scout. Proxy owns DNS resolution,
  all-answer public-IP checks, numeric destination pinning, and peer verification.
- Public HTTP destination port 80 and HTTPS destination port 443 only. These are
  two allowed destination ports, not the entire 80–443 range.
- Firewall blocks direct/DNS bypass. Proxy blocks private/local/reserved and
  cloud-metadata addresses, including redirected/background connections.
- HTTPS remains end-to-end; proxy is not inspecting encrypted page contents or
  classifying button effects. Network permission is not action permission.
- Narrow local browser-control exception at `127.0.0.1:9222`, plus established
  replies. Ordinary webpage traffic cannot use this control endpoint.
- Sanitized persistent best-effort protection logs: 5 MiB per file and three
  backups by default; size/count/verbosity configurable through existing file.
  Open/write/rotation failures attempt fixed diagnostics, not permission bypass.
  No universal logging-failure detection or tamper-proof persistence guarantee.

Existing verification receipt: [protection-verification.json](../../../stuff/protection-verification.json).
This documentation pass does not rerun or extend that verification.

Not implemented by this discussion: LLM browser reviewer, model-driven browsing,
pre-review preparation, post-approval recheck, explicit download denial, separate
Chromium container, research missions, media ingestion, or percentage budgeting.

## 3. Reviewer purpose and limits

Agreed direction: a separate LLM reviews proposed browser actions before they
execute. One general, effect-based reviewer; not a separate safety model or
policy implementation for each action name.

Revised on 2026-09-16: reviewer evaluates safety only, not contribution to the
research goal. Hermes's research LLM owns planning, continuity, and goal relevance.
This supersedes the earlier requirement for reviewer to assess both safety and
goal contribution.

Reviewer evaluates:

1. Whether likely effects comply with the trusted safety/permission policy.
2. Whether evidence is sufficient to approve rather than guess.

A harmless but off-topic action is not rejected merely for irrelevance by this
safety-only reviewer. Conversely, relevance cannot authorize a forbidden effect
such as purchasing a subscription. Reviewer is not an independent research-quality
or goal-drift checker under the revised role.

### Research-only approval baseline — confirmed

Confirmed on 2026-09-16 for the current anonymous-browsing phase:

- Reviewer may approve searches, filters, menus, pagination, opening content,
  and media playback when evidence supports permitted effects. Under the revised
  safety-only role, Hermes owns whether these actions advance the research goal.
- Reviewer must deny purchases, account creation/login, posting, messaging,
  likes/follows, uploads, and account changes.
- Unclear effects remain denied under the existing uncertainty rule.

These are effect-based policy categories, not an allowlist of button labels or
automatic permission for every action with one of these names. Review coverage
and hard network/download/tool boundaries still apply independently.

### Cookie consent — accept all permitted

Confirmed on 2026-09-16: Scout may choose Accept all on ordinary cookie-consent
prompts, including optional tracking/personalization. No requirement to seek
necessary-only settings or skip content solely because optional cookies require
consent. User prefers discovery of more relevant AI media over an unbiased sample
and accepts the additional bandwidth overhead.

Consent clicks still undergo the same action review. This permits cookie consent,
not unrelated bundled purchases, logins, uploads, account actions, or browser/OS
permissions. Existing network, download, sandbox, and resource limits remain.
Accepting cookies does not authorize persistence of browser profiles across runs
or change the local review-evidence retention policy.

Webpage labels alone do not prove effects. Reviewer considers visible context,
target/link/form information, typed content or requested key, and intended action.
It cannot know every server-side consequence or hidden JavaScript handler.

Reviewer helps resist misleading instructions and unwanted agent actions. It is
not antivirus, an exploit detector, or a replacement for code-enforced boundaries.
Website can exploit a rendering/JavaScript/media bug without saving a downloaded
file. Conversely, posting, purchasing, or changing an account can cause harm
without any software vulnerability. Each needs different protections.

User remains committed to building Scout. Commercial-agent research was for
learning click-safety patterns, not choosing a replacement product.

## 4. Action coverage

| Action | Discussion outcome |
| --- | --- |
| Click a webpage element | Selected for review. A webpage button labeled Back is still a click. |
| Navigate to a new URL | Selected for review; proxy/firewall checks still apply independently. |
| Type into a field | Explicitly selected for review. Review whole text-entry action, not each character. |
| Browser keypress | All keys selected for review, not only Enter. This is browser input, not OS-wide keyboard control. |
| Native browser-history Back | Explicitly exempt from LLM review. Existing network protections remain. |
| Native scroll | Explicitly exempt from LLM review. Hard security controls still apply. |
| Page snapshot, screenshot, image URL enumeration, browser close | Explicitly exempt from LLM review. Does not grant arbitrary JavaScript or filesystem access. |
| List or switch existing browser tabs | Explicitly exempt from LLM review. Switching does not exempt subsequent reviewed actions in the selected tab. |
| Terminal, arbitrary JavaScript, filesystem, uploads, messaging, MCP, delegation, scheduling | Not granted by browser-review discussion; no alternate route around browser policy. |

Hermes separates `browser_type(ref, text)` from `browser_press(key)`. Text entry
and Enter therefore produce separate review requests; no action batching approved.

Typing can trigger live search/autosave before Enter; keys can submit forms or
activate focused controls. "We intend to type only searches" is not a universal
safety guarantee. Native scroll/history can also trigger webpage events; exemptions
are a practical review boundary, not proof of zero side effects or unchanged pages.

Configurable coverage requested. Proposed explicit modes:

- `blocked`: cannot execute, regardless of reviewer preference.
- `review_required`: requires valid approval for that exact action.
- `allowed_without_review`: deliberate exemption, still subject to hard controls.

Removing an action from review must not silently enable it. Confirmed missing or
unknown action behavior: deny. Final configuration schema remains part of the
unconfirmed brief; new action types need an explicit permission rule. Browser-only
review does not expand other tool permissions. Scroll/observation/close exemptions
and default-deny were confirmed on 2026-09-16; native Back was confirmed earlier.

### New tabs and popup windows — confirmed

Confirmed on 2026-09-16:

- Allow new tabs/popup windows under the same network protections and download
  denial. Here popup means a browser window, not an overlay within a webpage.
- Keep Scout's selected tab unchanged until Scout explicitly switches. Listing
  and switching existing tabs require no LLM review.
- Clicks, typing, all keys, and new-URL navigation still require review inside
  whichever tab Scout selects. Switching is not approval of that tab's content.

Background tabs can load and execute webpage code before selection; this policy
does not quarantine them. Proxy denial blocks a connection, not tab creation:
a tab may remain blank or display a load error when its destination is blocked.
Do not infer popup blocking merely because no new tab was observed.

Implementation findings, not additional user-approved behavior: the pinned
driver tracks stable tab IDs, URLs, and titles, and its `add_page` method selects
the added page. Preserving Scout's selection needs explicit enforcement rather
than assuming driver defaults do so. Driver launch includes
`--disable-popup-blocking`, which Scout's current launcher permits; native popup
blocking is not an existing safety guarantee. New-tab notifications and handling
of a selected tab that closes still need implementation detail in the brief.

## 5. Proposed execution architecture

```text
Hermes proposes action
  -> Scout guarded browser handler checks action policy
  -> prepare relevant context
  -> capture viewport and build review packet
  -> separate LLM approves / denies / reports uncertainty
  -> code rechecks approved context
  -> execute exact approved action through existing browser driver
  -> return result and record permitted metadata/usage
```

Core sequence accepted in discussion; exact interfaces and edge cases remain open.

Recommended implementation lives in Scout plugin around existing browser harness.
Expose guarded operations only, not a generic raw driver/JavaScript command tool.
Test bypass paths, not only the list of visible model tools. Core Hermes changes
are not currently justified; report a real integration blocker before expanding
scope. Reuse browser machinery rather than replacing it.

Hermes findings affecting implementation:

- Native tool dispatch and plugin registration already exist.
- Pre-tool hooks and execution middleware exist, but some callback exceptions are
  logged and execution continues. A hook alone is not a proven mandatory gate.
- `ctx.register_tool(...)` supports plugin tools; built-in overrides require
  operator opt-in. Exact registration/override approach not selected yet.
- `ctx.llm.complete_structured(...)` accepts separate text/image inputs and
  structured results. Reviewer need not share full research-agent history.
- Native structured validation depends on optional `jsonschema`; Scout must not
  assume invalid output is rejected without ensuring validation.
- Host model routing/fallback behavior needs verification against the agreed
  no-fallback reviewer failure rule. Do not silently substitute provider/model.

## 6. Preparation and screenshot context

Every reviewed action receives a full visible-viewport screenshot for the initial
experiment. Not the full scrollable document and not every page on the website.

Preparation cannot be identical for every action:

| Action | Proposed preparation |
| --- | --- |
| Click | Resolve target, scroll into view if needed, verify visible and unobstructed. |
| Type | Resolve input and scroll into view; do not type or change focus merely to prepare. |
| Keypress | Inspect existing focus. Reveal relevant focused element if needed without changing focus; page-level keys may have no element target. |
| Navigate | Include requested destination URL and current-page screenshot. Cannot show destination before visiting it; scrolling is not inherently required. |

Preparation is deterministic code, not another model call. Proposed rule: no
preparatory click, typing, submission, or focus change. Confirmed missing-target
or still-covered-after-permitted-scrolling outcome: reject only the action and
return a reason to Scout; research may continue. No forced clicks, guessed targets,
or reused old screenshots. Exact target checks, including oversized, detached,
and iframe targets, still need contract/test detail.
This action-specific context collection does not make reviewer logic action-specific.

Important source findings:

- Element references may include elements outside viewport.
- Hermes forwards clicks to native driver. Pinned driver's normal click path
  resolves coordinates and dispatches mouse events without first scrolling.
  Earlier suggestion that this path automatically scrolls was corrected.
- Filling a field focuses it, which may scroll; this is not a pre-review guarantee.
- Current Hermes `browser_vision` captures with `--full` on normal native path
  and can invoke vision processing or embed image into main model history.
  Proposed reviewer needs capture-only viewport path, not accidental extra vision
  calls or full-page images through that tool.

Proposed safety-only review packet: trusted safety/permission policy; exact action
and arguments; current page/tab identity; target/link/form/focus details as
applicable; fresh viewport image. Include enough current state to assess effects,
not just a button label or Hermes's assertion that it is safe. Exact schema/size
limits remain open. Page text, screenshot, DOM metadata, and agent explanations
are evidence, not policy authority. Reviewer gets no tool execution powers.

Confirmed on 2026-09-16: operator supplies the research goal when starting a run.
Scout chooses sites, searches, and exploration steps independently. For this first
version, changing the goal requires a new run. The safety-only revision removes
reviewer's goal-relevance duty and the requirement to send the full mission goal
for that purpose. Trusted safety permissions remain independently supplied, not
defined by Scout or webpage instructions. Messaging updates and mission-control
remain outside this slice.

### Reviewer lifecycle — fresh safety-only calls confirmed

Confirmed on 2026-09-16 after the role revision: use a fresh independent
safety-review request for each covered action, without a growing reviewer
conversation or automatic carryover of prior reviews. This supersedes the earlier
persistent per-run reviewer decision. Hermes retains research context and owns
goal relevance; reviewer assesses safety/permission compliance only.

This is a new model request, not starting a new model/container/process for each
action. The last-ten-record window was never confirmed; reviewer-history trimming
and summarization are not implementation requirements for this slice.

Fresh review still needs safety-relevant state, such as existing form values and
submission destination when reviewing Enter. Insufficient evidence remains denial;
do not assume isolated action names reveal all effects. Required context must come
from explicitly supplied evidence, not an assumed reviewer memory.

Hermes's structured completion interface builds a new text/image message list per
call and supports this direction. Reuse existing host model/auth interfaces.
No accumulated old screenshots or persistent raw transcripts remain authorized,
and previous approval is not proof of execution success or permission to act again.

### Reviewer timeout and configuration — confirmed direction

Confirmed on 2026-09-16: review-request timeout is 5 minutes (300 seconds),
replacing the proposed 60-second value. All discussed operating settings must be
config-file driven, not hard-coded in implementation. Covered settings include
reviewer model/reasoning/timeout/retries, viewport/device scale, action review
policy, logging, and applicable operating limits. Initial agreed values belong
in the configuration file; implementation reads and validates them rather than

Existing source config is [config.yaml](../../../docker/signal-scout/config.yaml),

not an unrelated second source of values. Configuration is trusted operator input,

Confirmed on 2026-09-16: initial automatic reviewer retry count is `0`, configurable

No lifecycle choice can authorize approval reuse or bypass review/recheck. Any
performance trial still requires a confirmed brief; no token/latency savings

## 7. Headless browser, dimensions, and usage experiment

Current browser is real Chromium running headlessly: renders pages in memory,
runs JavaScript, and produces screenshots without visible desktop window.
Headless does not mean text-only. Host monitor size does not set its viewport.

Confirmed on 2026-09-16: fixed viewport of 1280×720 CSS pixels at device scale
factor 1 across every tab for the initial experiment. Capture the visible viewport
as a 1280×720-pixel image; no full-page capture or automatic cropping. Driver
supports `set viewport 1280 720 1` in the owned session. Verify actual viewport and
captured pixel dimensions, including new tabs. Do not treat launcher
`--window-size=1280,720` alone as proof of capture dimensions.

Tradeoff: screenshot per review improves visual context but adds input usage and
review latency. 100 clicks/hour is at least 100 reviews; typing, keys, and separate
navigations add more. It is not automatically a 100-review/hour total.

Previously discussed illustrative estimate, not measured Scout usage:

- Under the stated `gpt-5.6-luna` image-token assumptions, 1280×720 image ≈ 1,104
  image tokens; 100 such reviews ≈ 110,400 image-input tokens.
- Assuming another 1,000 text-input tokens per review gives ≈ 210,400 input tokens
  per 100 reviews, before output/reasoning, research-agent calls, and other work.
- `gpt-5.6-luna` was only a bootstrap-based example when this estimate was made;
  it has since been selected for initial review. That choice does not validate
  the estimate. Resolution, model, detail, resizing, and caching affect results.
- PNG/JPEG byte size is not itself model image-token count. No screenshot files,
  actual sizes, reviewer usage, or live experiment were measured in this discussion.
- No valid conversion from these estimates to a percentage of subscription exists
  in the current plan. Preserve unknown usage rather than pretending it is zero.

Confirmed experiment choice: include screenshot on every review initially, measure
usage, then decide permanent policy. Permanent choice explicitly deferred in
shared `daily_log/deferred-decisions.md`. Viewport/device scale and initial
reviewer model/reasoning are confirmed; remaining image processing, experiment
size, and live-call allowance remain unconfirmed.

### Review evidence retention — confirmed

Confirmed on 2026-09-16:

- No persistent review screenshot archive or raw reviewer transcripts.
- Remove temporary review screenshots after use.
- Persist only action type, verdict, sanitized reason, timing, and usage counts
  through the existing rotating-log system. No raw page content or typed text in
  review logs; do not persist raw review packets instead of transcripts.

This policy limits Scout's local retention, not what is transmitted for review:
the reviewer model still receives the screenshot and required review context.
It makes visual debugging less complete while reducing retained sensitive data.

## 8. Verdicts, failures, and post-approval recheck

| Outcome | Agreed behavior |
| --- | --- |
| Valid approve | Execute only after code-based context recheck passes and other controls permit action. |
| Valid deny | Do not execute; return short sanitized reason and best-effort record. Research may continue. |
| Valid uncertain | Treat as denial; gather evidence or research elsewhere rather than guess. |
| Reviewer timeout/provider error/invalid response | Block pending action, end mission as failed, close browser, and report failure. No automatic approval, fallback reviewer, or mission restart. |
| Target missing or still covered after permitted scrolling | Reject pending action and return a sanitized reason to Scout. Research may continue; no forced click or guessed target. |
| Required screenshot fails or safety checks cannot run | Block pending action and stop current browsing run. No blind execution or reuse of an old screenshot. |
| Relevant context changed during review or before execution | Cancel pending action, invalidate approval, and return a sanitized context-changed result to Scout. No automatic retry/re-review; browsing run may continue. Scout can inspect current state and propose a fresh action requiring fresh review. |

Recheck explicitly confirmed: compare relevant page/tab, target identity and
properties (label/link/form as appropriate), visibility/obstruction, and keyboard
focus for key actions. It is code, not a second LLM review. Do not compare every
screenshot pixel; moving video/blinking cursor need not invalidate approval.

Example: reviewer approves View demo, but target disappears or popup covers it
while review runs. Do not execute old approval against changed context.

Confirmed on 2026-09-16: stale-context recovery belongs to Scout's next decision,
not an automatic retry loop inside the browser handler. Returning control does
not permit reuse of the old approval or automatic execution against a new target.

Also confirmed: ordinary webpage obstacles block one action, while failure of
required capture or safety-check machinery stops browsing. A completed check
that finds a changed target is different from inability to perform the check.
This does not change the existing best-effort logging policy.

Limit: checks cannot freeze webpage or prove hidden/server-side effects. Page can
change between check and action. Exact comparison criteria, failure detection,
startup enforcement details, remaining timeout interactions, and provider retry
behavior still need final specification. Reviewer timeout is confirmed at 300
seconds through configuration; all settings must preserve agreed failure outcomes.

## 9. Download denial and storage lifecycle

Confirmed requirement: `Browser.setDownloadBehavior` with `behavior: "deny"`
before untrusted browsing, covering all browser contexts. Independent of LLM
approval: approved click can still have its download blocked by browser policy.
Not implemented yet.

Denial blocks browser file-download operations, not normal page/media fetching.
Rendering HTML, executing webpage JavaScript, decoding images/video, or viewing
supported inline documents can still expose browser bugs. Download denial is
neither malware scanning nor a ban on receiving network bytes.

No download path is required for deny policy. Pinned driver's download-path option
also sends `behavior: "allow"`; do not set that option and accidentally undo deny.
If allowed downloads become a future feature, a possible destination is
`/tmp/scout-downloads` in browser-local temporary storage, with explicit limits and
processing policy. This path/feature is illustrative, not approved implementation.

Current storage distinctions:

| Location | Lifecycle and limit |
| --- | --- |
| Scout `/tmp` tmpfs | Cleared on container stop/restart; finite capacity; `noexec,nosuid,nodev`. Not a claim of forensic secure erasure. |
| `scout-auth` at `/var/lib/scout` | Writable persistent named volume; survives ordinary restart/replacement. |
| `scout-logs` at `/var/lib/scout/logs` | Writable persistent named volume; survives ordinary restart/replacement. |
| Ordinary Docker writable layer | Generally survives restart, disappears on container removal. Scout root filesystem is read-only, with explicit writable mounts above. |

We have not established a verified download destination in existing runtime.
"Downloads normally go into Downloads" is not a security boundary. Ordinary page
cannot freely write arbitrary local files; a compromised process with sufficient
permissions may access other writable paths. `noexec` is not a universal guarantee
against interpreted code or in-memory exploits. Cleanup cannot undo prior theft
or external account actions.

Current browser parent and Hermes share container user; browser-sandbox escape
could expose credentials accessible to that user without Docker escape. This is
why filesystem isolation from Hermes credentials was raised separately.

## 10. Separate browser container — confirmed direction

Confirmed on 2026-09-16: run Chromium and Hermes in separate runtime containers
on the same VPS. This separates browser access from Hermes credentials/storage;
it does not require a second VPS. Intended boundary for the implementation brief:

- Hermes container owns research/reviewer execution, model credentials, and
  research storage.
- Chromium container owns browser and disposable profile/temp storage. No Hermes
  authentication/research volumes and no Docker socket mounted there.
- Hermes initiates restricted private browser-control connection. Return text and
  screenshots through connection rather than shared writable directory.
- No publicly published control endpoint. Page traffic remains under proxy and
  firewall protections; private Docker network alone is not enough enforcement.
- Browser container cannot initiate arbitrary connections into Hermes. Established
  control replies remain necessary; connection is not physically one-way.
- Retain Chromium sandbox, non-root/read-only restrictions, resource limits,
  download denial, and fresh identity. Do not trade these away for separation.

Benefit: browser compromise loses direct filesystem access to Hermes-mounted
credentials. Limits: shared kernel, exposed control/client parsing surface, and
untrusted browser results still exist. If source accounts are added later, their
browser-held cookies remain exposed to compromise of that browser.

Current Scout intentionally rejects external attachment and requires local owned
Chromium with loopback-only control. Split requires explicit startup/control and
network-policy changes, retained sandbox attestation, revised SS-S001/SS-S002
contracts, and adversarial tests. Not just adding another Compose service.

User approved the runtime split, not a complete implementation brief. Resolve
control/startup details from existing source and specify them in that brief before
changing Compose, volumes, control endpoint, or firewall. No runtime change yet.
Separate runtime browser is different from a separate testing stack. Prior decision
was to test existing runtime services, not build a duplicate dedicated test setup.

### Slice 1 working architecture — proposal, 2026-09-17

- Keep Hermes and its existing `agent-browser` driver in the Hermes container;
  move Chromium and its owned-process launcher to the browser container.
- Prefer reusing native remote-CDP support over inventing a browser command
  protocol. Browser-side launcher checks its own Chromium child; Scout verifies
  required sandbox status before untrusted navigation. Exact restricted endpoint,
  authentication/access-control, and any local-CDP relay wiring still need design
  and tests. An endpoint response alone is not ownership proof.
- Give Hermes and browser distinct network namespaces with separately enforced
  firewall rules, reusing the existing firewall helper approach. Permit only the
  designated Hermes-to-browser control connection and its replies, plus each
  component's permitted proxy traffic. Do not put both application containers in
  the same shared network namespace. Public-web proxy policy remains unchanged.
- Keep auth/research mounts exclusive to Hermes. Browser profile and temporary
  state remain browser-local and disposable; return browser results through the
  control connection, not a shared writable artifact directory.
- Startup/control/sandbox enforcement failures cannot select a local fallback or
  different browser. Existing fail-closed requirements remain; this does not
  change best-effort logging behavior or implement the later reviewer.

Confirmed on 2026-09-17: no concurrent Scout runs for now. One active browser
session/run may contain multiple tabs; do not implement parallel-run support or a
queue. The recommendation is to reject a second claimant clearly, never silently
attach it to the first run's browser.

Also confirmed: browser starts on mission start and ends on mission end. This
is extended by the disposable browser-container decision below. Slice 1 must
